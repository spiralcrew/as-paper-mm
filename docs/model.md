# Модель, калибровка и симуляция исполнения

Документ описывает, что именно реализовано, откуда взята каждая формула и где модель
упрощает реальность. Ссылки на статью — по версии Avellaneda & Stoikov от 5 октября 2006
(опубликована в Quantitative Finance, 2008); номера формул — по ней.

## 1. Avellaneda–Stoikov: котировки

Mid-цена — арифметическое броуновское движение `dS = σ dW` (2.1). Агент максимизирует
`E[−exp(−γ(X_T + q_T S_T))]` (3.1). Асимптотическое решение по инвентарю (§3.2):

    r(s, q, t) = s − q·γ·σ²·(T − t)                          (3.17)  резервационная цена
    δᵃ + δᵇ    = γ·σ²·(T − t) + (2/γ)·ln(1 + γ/k)            (3.18)  оптимальный спред

Котировки: `bid = r − (δᵃ+δᵇ)/2`, `ask = r + (δᵃ+δᵇ)/2`.

| Символ | Смысл | Единицы в проекте |
|---|---|---|
| s | mid-цена BTCUSDT | USDT |
| q | инвентарь в лотах (позиция / `order_qty`) | лоты, со знаком |
| γ | неприятие риска | 1/USDT |
| σ | волатильность mid-цены | USDT/√s |
| T − t = τ | время до конца сессии | секунды |
| k, A | параметры интенсивности λ(δ) = A·e^(−kδ) (3.8) | 1/USDT, 1/с |

Реализация: `include/asmm/avellaneda_stoikov.hpp` (`reservation_price`, `optimal_spread`,
`compute_quotes`).

## 2. Воспроизведение эксперимента статьи (§3.3, таблицы 1–3)

`asmm_sim` (`include/asmm/as_simulation.hpp`) повторяет процедуру статьи дословно: s = 100,
T = 1, σ = 2, dt = 0.005, q₀ = 0, k = 1.5, A = 140, 1000 траекторий. На шаге t считаются
котировки; с вероятностью λ(δᵃ)dt продаём 1 по s + δᵃ, с вероятностью λ(δᵇ)dt покупаем 1 по
s − δᵇ; mid сдвигается на ±σ√dt. «Symmetric» — тот же спред вокруг mid. Прибыль
`X_T + q_T·S_T`.

В таблицах статьи спред постоянный: 1.33 / 1.29 / 1.15 для γ = 0.01 / 0.1 / 0.5. Это ровно
`(2/γ)·ln(1 + γ/k)`, то есть член `γσ²(T−t)` из (3.18) в эксперименте, по-видимому, не
использовался. Поэтому `asmm_sim` печатает оба варианта. Вариант с постоянным спредом
(1000 траекторий, seed 42) против статьи:

| γ | стратегия | спред | прибыль | std(прибыли) | конечный q | std(q) |
|---|---|---|---|---|---|---|
| 0.01 | inventory: наш / статья | 1.33 / 1.33 | 67.57 / 66.78 | 8.86 / 8.76 | −0.20 / −0.02 | 5.39 / 4.70 |
| 0.01 | symmetric: наш / статья | 1.33 / 1.33 | 67.68 / 67.36 | 13.88 / 13.40 | −0.13 / −0.31 | 9.10 / 8.65 |
| 0.1 | inventory: наш / статья | 1.29 / 1.29 | 63.81 / 62.94 | 5.91 / 5.89 | −0.19 / 0.10 | 2.96 / 2.80 |
| 0.1 | symmetric: наш / статья | 1.29 / 1.29 | 67.60 / 67.21 | 13.94 / 13.43 | −0.10 / −0.018 | 9.17 / 8.66 |
| 0.5 | inventory: наш / статья | 1.15 / 1.15 | **23.63 / 33.92** | 5.05 / 4.72 | −0.13 / −0.02 | 1.93 / 1.88 |
| 0.5 | symmetric: наш / статья | 1.15 / 1.15 | 67.18 / 66.20 | 14.21 / 14.53 | −0.07 / 0.25 | 9.36 / 9.06 |

Совпадение в пределах шума Монте-Карло (стандартная ошибка средней прибыли ≈ std/√1000 ≈
0.2–0.45) везде, кроме одной ячейки: средняя прибыль inventory-стратегии при γ = 0.5
(23.6 против 33.9). Дисперсии в этой строке совпадают. При γ = 0.5 и q ≠ 0 сдвиг r на
γσ²(T−t)·q = 2(T−t)·q доходит до нескольких долларов, и одна из котировок оказывается по
другую сторону mid (δ < 0, λ·dt > 1). Как авторы обрабатывали этот случай, в статье не
сказано — вероятная причина расхождения. Тест `AsSimulation.ReproducesPaperTable1` проверяет
таблицу 1 (γ = 0.1) с допусками, а `InventoryStrategyReducesRisk` — главный вывод статьи
(дисперсия прибыли и инвентаря у inventory-стратегии заметно ниже при сопоставимой прибыли).

С полным спредом (3.18) выводы те же: при γ = 0.1 inventory 64.5 ± 6.6 (std q 2.9) против
symmetric 67.1 ± 13.3 (std q 8.8).

## 3. Калибровка λ(δ) = A·e^(−kδ) по ленте сделок

В статье (§2.5, формула 2.11) экспонента выводится из степенного распределения размеров
рыночных заявок и логарифмического импакта: `λ(δ) = Λ·P(Δp > δ) = A·e^(−kδ)`, где Λ —
частота рыночных заявок, `A = Λ/α`, `k = αK`. Мы оцениваем ту же величину напрямую —
частоту, с которой рынок доходит до глубины δ от mid (`include/asmm/intensity.hpp`):

1. время режется на интервалы Δ = 1 с; в начале интервала фиксируется mid s₀;
2. за интервал запоминается максимальная глубина агрессоров: `Dᵃ = max(p − s₀)` по покупкам,
   `Dᵇ = max(s₀ − p)` по продажам (обе стороны — наблюдения одной величины, λᵃ = λᵇ (3.8));
3. заявка на глубине δ исполнилась бы, если `D ≥ δ`; доля таких интервалов `P̂(δ)`, и для
   пуассоновского потока `λ̂(δ) = −ln(1 − P̂(δ)) / Δ`;
4. МНК `ln λ̂(δᵢ) = ln A − k·δᵢ` по 15 точкам сетки; окно 900 интервалов (15 минут).

Сетка — квантили положительных глубин, от мелкой до самой глубокой, где ещё есть ≥ 5
попаданий. Это важно на реальных данных: цены дискретны (тик 0.01), поэтому глубины кратны
половине тика, и эмпирическая функция выживания ступенчатая — точки сетки должны стоять на
её скачках. Первая версия брала равномерную сетку до 90-го перцентиля, и на тихом BTCUSDT
она вырождалась: 90-й перцентиль равен 0.005 (полтика), оценка давала k ≈ 63 при R² ≈ 0.19.
С квантильной сеткой на тех же данных k ≈ 0.94–1.00 1/USDT, A ≈ 0.7–0.8 1/с, R² ≈ 0.97–0.98.

Распределение глубин в тихом режиме двугорбое: в ~37% секундных интервалов агрессоры задевают
только лучшую цену (δ = 0.005), дальше — пусто, затем редкие скачки цены на 3–15 USDT. Если
экспонента описывает окно плохо (R² < 0.6), оценка не используется и движок котирует с `--k`
(в итоге пишется «no reliable fit yet, using --k»). Используемый k ограничен `[k_min, k_max]`.
Тесты:
`IntensityEstimator.RecoversKnownParameters` (k и A восстанавливаются по синтетике с
известными параметрами с точностью 5% и 10%), `EndToEndFromSyntheticTape`.

## 4. Волатильность

EWMA дисперсии приращений mid в единицу времени: `v ← (1 − α)·v + α·(Δs)²/Δt`,
`α = 1 − 2^(−Δt/h)`, σ = √v сразу в USDT/√s. Сэмплирование не чаще 1 с: на тиковой
частоте bid–ask bounce завышает реализованную дисперсию (Zhang, Mykland, Aït-Sahalia, 2005).

## 5. Локальная книга заявок

`include/asmm/order_book.hpp` — L2-книга по правилам Binance «How to manage a local order
book correctly»: снимок REST `GET /api/v3/depth` с `lastUpdateId`; обновления с
`u ≤ lastUpdateId` отбрасываются; `U > lastUpdateId + 1` — разрыв, нужен новый снимок;
иначе уровни применяются (объём 0 — удалить), `lastUpdateId = u`. Цены хранятся в целых тиках.

Проверка на реальных данных: `bookTicker.u` и `depthUpdate.u` — одна последовательность id
стакана Binance. Тест `OrderBookOnRealData.MatchesBookTickerAtSameUpdateId` в каждой точке,
где id совпадают, требует точного совпадения лучших цен и объёмов книги с bookTicker.

## 6. Симуляция исполнения (paper trading)

Реальных заявок нет. `include/asmm/paper_exchange.hpp` моделирует биржу:

**Очередь (FIFO, price-time priority), `--fill-model queue` — по умолчанию.** Заявка встаёт в
хвост уровня: `queue_ahead` = видимый объём уровня в момент, когда заявка дошла до биржи.
- Сделка по нашей цене со «своей» стороны агрессора (агрессор-продавец бьёт биды):
  сначала съедает `queue_ahead`, остаток исполняет нас (частично или полностью).
- Сделка хуже нашей цены (агрессор прошёл уровень насквозь) — уровень исчерпан, мы исполнены
  полностью.
- Уменьшение объёма уровня в стакане без сделок — отмены чужих заявок. `--cancel-model
  proportional` (по умолчанию): отменено равномерно по очереди, `queue_ahead` уменьшается на
  долю `queue_ahead / level`. `pessimistic`: отменяют только стоящие за нами, `queue_ahead`
  лишь ограничивается объёмом уровня. Рост уровня — новые заявки встают за нами.
- Перестановка на ту же цену сохраняет место в очереди; на новую цену — снова в хвост.
  Поэтому движок не двигает заявку, пока новая цена отличается меньше чем на
  `--requote-ticks` тиков.

Модели `touch` (сделка по нашей цене исполняет сразу, оптимистичная граница) и `through`
(сделки по нашей цене не исполняют, пессимистичная) оставлены для сравнения. Пробой уровня во
всех трёх моделях исполняет заявку целиком.

**Задержка `--latency-ms`.** Заявка становится живой через latency после отправки; отмена
или перестановка тоже вступает в силу через latency, и до этого старая котировка может быть
исполнена — риск «устаревшей котировки» (adverse selection на задержке).

**Проскальзывание.** Лимитные заявки исполняются по своей цене. Рыночные заявки
(ликвидация инвентаря в конце данных; с `--liquidate-session` — в конце каждой сессии T, как
терминальное условие статьи) проходят по уровням стакана: VWAP, число съеденных уровней,
проскальзывание `|VWAP − mid|·qty`, комиссия тейкера (`--taker-fee`, 0.1% у Binance VIP0).
Если видимой ликвидности не хватает, остаток исполняется по худшей видимой цене с флагом.

**Метрики.** `edge captured` — Σ(mid − цена) по покупкам и Σ(цена − mid) по продажам в момент
исполнения: сколько спреда заработано до изменения цены. Итоговый PnL — mark-to-mid после
ликвидации.

**Допущения (честно).** Наши заявки не влияют на рынок; рыночные данные приходят без
задержки (задержка только у наших заявок); отмены распределены по выбранной модели, позиция
внутри уровня не наблюдается; сделки и обновления стакана приходят из разных стримов, и если
обновление уровня пришло раньше сделки, сделка может быть учтена в очереди дважды
(оптимистичный сдвиг; pessimistic-модель отмен его не делает).

## 7. Как проверено на живых данных

Все прогоны — на реальных данных Binance; после проверки данные удалены, в репозитории только
5-минутный тестовый сэмпл (`data/sample_btcusdt.jsonl`).

| Проверка | Результат |
|---|---|
| Независимая реконструкция книги на Python (Decimal) по записи сборщика, сравнение с bookTicker при одинаковом `update_id` | 0 расхождений в 147 (сэмпл) и 211 (10-минутный прогон) точках, 0 разрывов |
| То же в C++ (`OrderBookOnRealData.MatchesBookTickerAtSameUpdateId`) | 0 расхождений |
| 10 минут живого paper trading с реальными обрывами сети (DNS, keepalive timeout) | сборщик переподключился, взял новые снимки; в `asmm` 4 снимка, 0 разрывов, книга синхронизирована |
| Ротация файлов записи (в т.ч. gzip) | каждый файл начинается со своего снимка и проверяется отдельно: 0 разрывов, 0 расхождений |
| Детерминизм: реплей записанных файлов против живого прогона | исполнения совпали построчно (CSV), итоговый PnL идентичен |
| Калибровка λ(δ) на реальных данных | k ≈ 0.94–1.00 1/USDT, R² ≈ 0.97–0.98 |

Наблюдения по симуляции на сэмпле (γ = 0.001, T = 30 с, 1 лот = 0.001 BTC, калиброванный
k ≈ 0.94, мейкер-оборот в USDT):

| Задержка | touch | queue | through | edge (queue) |
|---|---|---|---|---|
| 0 мс | 227 | 227 | 152 | +0.0011 USDT |
| 50 мс | 834 | 682 | 682 | −0.0374 USDT |

- объём упорядочен как touch ≥ queue ≥ through (это же проверяет тест
  `QueueModel.FillModelsAreOrderedTouchQueueThrough`);
- котировки стоят примерно в 1 USDT от mid, поэтому queue почти всегда исполняется пробоем
  уровня и совпадает с through;
- задержка 50 мс увеличивает оборот и делает edge отрицательным: неснятые вовремя котировки
  «снимает» рынок при движении цены (adverse selection на задержке).

У строк сборщика `recv_ms` может идти не по возрастанию: обновления стакана, накопленные
до снимка, записываются после него со своим исходным временем. Движок использует
монотонные часы `max(recv_ms)`, поэтому на расчёты это не влияет.

## 8. Практические отступления от статьи

- **Скользящий горизонт.** Сессии длиной T идут подряд, τ убывает от T до 0 и сбрасывается;
  инвентарь между сессиями переносится (или закрывается рыночной заявкой с `--liquidate-session`).
- **Лоты.** q — в лотах `order_qty` (в статье — в штуках акций, сделка = 1 штука).
- **Сетка цен и post-only.** Бид вниз, аск вверх к шагу 0.01; бид не выше `best_ask − tick`,
  аск не ниже `best_bid + tick`.
- **Лимит инвентаря.** |q| ≤ `max_inventory_lots`, объём стороны урезается до остатка.

## 9. Источник данных

Binance Spot, публичные стримы, ключи не нужны (`scripts/binance_feed.py`):

    wss://stream.binance.com:9443/stream?streams=btcusdt@bookTicker/btcusdt@trade/btcusdt@depth@100ms
    https://api.binance.com/api/v3/depth?symbol=BTCUSDT&limit=1000

Документация: https://developers.binance.com/docs/binance-spot-api-docs/web-socket-streams.
На Binance.com нет спот-пары BTC/USD; долларовая цена BTC — пара **BTCUSDT**.
Сборщик добавляет `recv_ms` (у bookTicker в споте нет времени), буферизует обновления стакана
до снимка, проверяет непрерывность `U/u` и при разрыве или ротации файла берёт новый снимок.
